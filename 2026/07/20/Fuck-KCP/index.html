Architecture

KCP segment

  • conv: session id, identity each session, stateful design
  • cmd: command, like PUSH, ACK, WASK, WINS.
  • frg: Number of fragments remaining after this segment in the same application message. The last fragment has frg = 0.
  • wnd: The sender’s currently available receive window, measured in segments.
  • ts: timestamp. The miliseconds the frame was packed by sender.
  • sn: serial number. Like TCP’s SN. For ACK, it explictly represents the received segment.
  • una: The next sequence number that the sender of this header expects to receive. All segments with sn < una have been cumulatively acknowledged.
  • len: length of payload.

Q: Does it has same ts value in ACK frame and the raw sended frame?
A: Yes. When receiving a PUSH segment, KCP stores its (sn, ts) in acklist. ikcp_flush() later copies the same ts into the corresponding ACK segment.
Q: what’s the rto?
A: RTO is the amount of time KCP waits for an acknowledgement before retransmitting an unacknowledged segment. It is estimated from the smoothed RTT and RTT variation.
Q: What’s the IKCP_FASTACK_CONSERVE marco using for in the process of IKCP_CMD_ACK?
A: When IKCP_FASTACK_CONSERVE is enabled, an ACK increments the fastack counter of an earlier unacknowledged segment only if ack.ts >= segment.ts. This prevents a stale or reordered ACK from being treated as evidence that a newer transmission was lost, making fast retransmission more conservative.

ikcp_input

Common processing for every valid segment:

  • rmt_wnd = wnd
  • parse_una(una)
  • shrink_buf()

IKCP_CMD_PUSH
• INPUT: A data segment sent by the peer
• MODIFY: ikcp_ack_push() records (sn, ts) in acklist; valid non-duplicate data is inserted into rcv_buf; contiguous data is moved from rcv_buf to rcv_queue
• OUTPUT: ikcp_flush() later sends an ACK

IKCP_CMD_ACK
• INPUT: An ACK for a previously sent segment
• MODIFY: Updates sender-side RTT/RTO; removes the explicitly acknowledged segment from snd_buf; recalculates snd_una; updates fastack counters of earlier unacknowledged segments
• OUTPUT: None directly; it may affect later retransmission and sending behavior

IKCP_CMD_WASK
• INPUT: The peer asks for my available receive window
• MODIFY: Sets IKCP_ASK_TELL in kcp->probe
• OUTPUT: ikcp_flush() later sends IKCP_CMD_WINS

IKCP_CMD_WINS
• INPUT: The peer announces its available receive window
• MODIFY: No branch-specific change; common processing has already updated rmt_wnd
• OUTPUT: None

Q: 为什么 IKCP_CMD_WINS 分支看起来什么都没做，但对端窗口实际上仍然得到了更新？
A: IKCP_CMD_WINS 分支本身不需要额外处理，因为在进入命令分支前，公共代码已经通过 kcp->rmt_wnd = wnd 保存了对端通告的可用接收窗口。后续发送时，本端会根据 rmt_wnd 限制能够进入发送状态的数据量
